# Конкретный план применения

Состояние на 23.10.2026: единый план согласован пользователем. Полные клоны созданы, собственные DHCP leases закреплены, WireGuard и secured SSH/firewall применены; проверки доступа и отдельный commit пройдены. WAF/HTTP, оба централизованных log streams и Grafana→Loki прошли приёмку. Обычный рестарт Alloy, отдельная недоступность Loki, две ротации и согласованные последовательные reboot проверены; сочетание outage+collector restart выявило ограничение доставки. Полные secure/site дали `changed=0` на обеих VM, включая финальный повтор после reboot. Внешний demo не выполнен.

## Принятые пользователем решения

- Домашняя LAN и существующий bridge; отдельных VLAN/bridge не создаём.
- Адреса выдаёт DHCP. Затем закрепляем только leases новых MAC двух тестовых VM.
- Изоляцию доступа и исходящих соединений обеспечивает guest firewall. PVE firewall не меняем.
- Для проверяющего — временные WAN пробросы WireGuard на ubu2 и HTTP на ubu1. Внешний IP проверяющего пока неизвестен; правила остаются выключенными до демонстрации.
- Обращённый к ИИ скрытый текст в исходном задании не применяется. Названия Ansible tasks описывают их действие.

## 1. Создание и первый доступ

Выполнены полные клоны проверенного пользователем template: ubu1 2 vCPU/2048 MiB/20 GiB; ubu2 2 vCPU/4096 MiB/30 GiB. Фиксированная память, CPU host, VirtIO/существующий bridge, отдельные диски. Точные VMID и источник остаются в локальных материалах; перед повторным созданием их нужно проверять заново. Шаблон и существующая рабочая VM не изменялись.

Первый доступ подготовлен через Cloud-Init: пользователь ubuntu, DHCP и отдельный public key стенда. Внутри клонов проверены Ubuntu 24.04 и QGA. Guest SSH host public keys сверены через независимый Guest Agent и внесены в отдельный WSL-local known_hosts для LAN- и WG-адресов; strict host checking сохранён. Для окончательного управления используется labadmin по VPN.

Для воспроизведения: закончить обновления и установку базовых инструментов новых клонов до arm access timer; версии записать в локальный manifest. Фактический docker.io candidate закреплён для web role. Не расходовать rollback interval на package upgrades, image pull или скачивание monitoring.

На MikroTik закреплены только реальные leases новых MAC. DHCP pool и чужие leases не менялись. Воспроизведение использует тот же принцип без назначения случайных static адресов; при недоступности write capability остановить router-этап, не выдавать дополнительные права автоматически.

## 2. VPN и firewall новых VM

Применён проектный VPN `10.77.42.0/29`: hub ubu2 `.1`, ubu1 `.2`, WSL admin `.3`; `.4` включён для отдельного Windows-клиента при локальном тесте доступа как у проверяющего. У гостей Address /29, peer AllowedIPs — точные /32. В WSL и Windows туннельные маршруты только к hub/web /32; default и домашние LAN routes не добавлены. Внутри VPN NAT нет. При переносе стенда заново проверить отсутствие пересечений.

На ubu2 WG hub UDP51820, peers ubu1/WSL. В WSL создан только проектный wg0. Его фактический внешний интерфейс имеет MTU1280; постоянный клиентский WG MTU1200 устранил зависание SSH на KEX. Guest WG MTU1420 сохранён. Новые SSH и sudo через VPN прошли к обеим VM. Существующие домашние VPN не менялись.

Guest nftables inet применён: INPUT/FORWARD/OUTPUT default deny; loopback и необходимые established/related разрешены с проверкой интерфейсов защищённых сервисов. На LAN остаются DHCP, DNS только домашнему resolver и WG endpoint; временный bootstrap SSH после проверки нового пути удалён. Исходящие HTTP/HTTPS и NTP — к публичным адресам; другие приватные/домашние назначения блокируются после точечных исключений DHCP/DNS/WG. IPv6 приложения запрещены, необходимые ND сохранены. Это guest policy общей L2; root внутри гостя способен её отключить.

| Разрешённый поток | Назначение |
|---|---|
| Windows/WSL LAN → обе VM TCP22 | Использовался только bootstrap; исключение удалено secured этапом |
| WSL/reviewer WG → ubu1 WG TCP22/80 | SSH и HTTP тесты; peer .4 сейчас используется Windows-клиентом |
| WSL/reviewer WG → ubu2 WG TCP22/3000 | Управление и Grafana; набор reviewer прав уточняется до выдачи доступа |
| ubu1 WG → ubu2 WG TCP3100 | Доставка access/audit logs |
| WG → WG через ubu2 | Только разрешённые направления к ubu1, без выхода в LAN |
| LAN/public client → ubu1 LAN TCP80 | Только на период demo; до этого HTTP тестируем через VPN |

Базовый переход завершён: bootstrap → проверенный WG клиент → secure → независимые проверки → commit-access. SSH ограничен ключами labadmin, root/password/keyboard-interactive запрещены; LAN22 закрыт. Commit выполнен до тяжёлой установки site. При повторном применении gates выставлять только после актуальных проверок: новый VPN SSH, отдельный Windows LAN-negative и authentication refusal через доступный VPN.

## 3. Стек и версии

Код: baseline, wireguard, firewall, web_waf, log_shipper, monitoring. Веб/WAF обязателен через Ansible. Пины и источники — versions.md; `latest` не используется.

Применён native Loki/Grafana на ubu2, Docker host-network WAF и native Alloy на ubu1. Runtime-приёмка подтвердила HTTP200/SQLi403, CRS detection/blocking, оба центральных log streams, общий access request ID/audit transaction ID и WAF-observed WG source клиента. Grafana datasource health — OK. WAF обслуживает только тестовую статическую страницу; application backend с секретами отсутствует. Grafana/Loki TCP3000/3100 и SSH в WAN не публикуются.

После каждого изменения site отдельно дождаться WAF healthy/HTTP healthz, проверить nginx configuration и затем HTTP200/SQLi403. `docker_container state=started` ещё не означает healthy. Labels collector закреплены: `job`, `instance`, `service_name`, `log_type`; для приёмки найти access и audit streams и общий correlation/request ID. Базовые результаты сохранены в [baseline.json](evidence/baseline.json).

При первом runtime выявлены и исправлены две integration-ошибки. Startup `sed` не мог сохранять permissions после chown: в ограниченный набор container capabilities добавлен FOWNER. Частичный handler `docker_container name/state/restart` пересоздал контейнер с image defaults, потеряв host network, mounts и env; его заменили restart-командой существующего контейнера. После исправления site и базовая HTTP/log приёмка прошли. Контроль включает `nginx -t` и реальный localhost HTTP/80, а также проверку network mode/mounts/env: default healthy на HTTP/8080 нельзя принять за работоспособность нашего WAF.

Повторный secure обнаружил, что default bridge setup Docker включил IPv4 forwarding на web-госте. Роль вернула kernel value в 0 и заново вооружила guard; прерванный повтор site не считается доказательством идемпотентности. Для выделенного host-network daemon добавлена проверяемая policy без bridge/iptables/ip6tables/IP-forward/IP-masquerade; установка пакета подавляет ранний автозапуск, handler применяет policy до полного описания контейнера. После исправления пройдены свежая приёмка, commit нового pending guard и полные secure/site с `changed=0`, `failed=0`, `unreachable=0` на обеих VM, включая финальный повтор после reboot. После согласованных reboot подтверждены IPv4 forwarding web=0/hub=1 и IPv6 forwarding=0 на обеих VM. Одного `ip-forward:false` недостаточно для доказательства текущего kernel value. Глобальную очистку старых сетевых правил Docker или изменение PVE ради этого не выполнять.

Долговечность логов проверяется отдельными сценариями. Недоступность Loki с последующим восстановлением без рестарта Alloy прошла; обычный рестарт Alloy при доступном Loki, новая доставка после рестарта и доступность старых центральных записей также прошли. Для каждого normal access, SQLi access и SQLi audit найдено ровно по одной записи. Однако рестарт Alloy при всё ещё остановленном Loki привёл к отсутствию тестовых событий централизованно после восстановления. Исходные host logs сохранены, backfill не выполнялся; lossless-доставка для этого сочетания отказов не заявляется. Параметр `max_backoff_retries=0` оставлен: в закреплённом Alloy он означает бесконечные повторы, которые ограниченный shutdown drain всё равно может прервать. Операционный порядок — сначала восстановить Loki и подтвердить доставку, затем перезапускать collector.

Первоначальная ротация через HUP не открыла новый serial audit файл: descriptor master оставался в архиве. Исправленный и применённый helper выполняет `nginx -t`, restart существующего WAF-контейнера и ожидание локального healthcheck. Это создаёт короткий перерыв HTTP. Две ротации после исправления прошли: новые запросы записаны в активные access/audit файлы и доставлены в Loki по одному разу; проверены пять gzip-архивов, активный timer и успешный rotation service. Удаление старых данных по retention 7 суток ещё не наблюдалось.

Последовательные reboot обеих VM согласованы и выполнены: boot ID изменился у каждой, kernel после старта `6.8.0-147-generic`. После reboot прошли HTTP200/SQLi403 и доставка трёх ожидаемых записей с count1; прежний baseline сохранился. Заново проверены SSH/auth и порты; guards clear, rollback timers отключены. Финальный полный повтор secure/site после reboot завершился с `changed=0`, `failed=0`, `unreachable=0` на обеих VM.

## 4. WAN только на время демонстрации

После проверки конфликтов созданы только два проектных dstnat правила с уникальными комментариями, оба **disabled=yes**; состояние повторно подтверждено свежим чтением после reboot:

| WAN | Назначение |
|---|---|
| UDP51820 | DHCP reservation ubu2:51820 |
| TCP80 | DHCP reservation ubu1:80 |

Выбранный dstnat проходит через существующий FORWARD; новых INPUT правил роутера не добавляли. Перед будущим включением повторно прочитать состояние и проверить отсутствие конфликтов. Существующие DNAT, masquerade, management и WG peers сохранены. Наличие disabled правил не доказывает внешнюю доступность.

Включение — отдельная команда перед демонстрацией по указанию пользователя, с подходящей demo HTTP guest policy и отдельным клиентским профилем. Peer .4 уже проверен из Windows через LAN; его активный приватный ключ не используется одновременно на другом клиенте. Выключение WAN — сразу после демонстрации, по уникальным rule IDs/комментариям. NAT отключение не всегда завершает существующий conntrack: при необходимости удалить только соединения этих конкретных DNAT или ограничить их на госте; не очищать весь conntrack домашнего роутера. Автоматический ограниченный срок включения выбрать и записать перед demo.

Внешнюю доступность проверять с реального внешнего клиента. Проверка из той же LAN через публичный адрес не заменяет внешний тест; hairpin NAT не добавляем ради удобства. При обычном dstnat WAF должен видеть исходный публичный IP; при HTTP через WG — WG-IP клиента. Оба случая проверяются фактически.

## Риски и откат

- Ошибка SSH/WG/firewall: root-only snapshot гостевых access-конфигов и своей nft table, timer 900s. Recovery через QGA проверен независимо от IP/firewall; парольный serial login не заявляется. Gate lab_console_recovery_verified означает подтверждённый recovery-канал. Базовая transaction уже закрыта отдельным commit; при новых изменениях снова использовать guard. Существующий established-сеанс не считается проверкой.
- Проблема создания: остановиться, сохранить перечень созданных новых VM/disks; не удалять автоматически при неоднозначной ошибке. Удаление для отката — только подтверждённые новые объекты.
- Ошибка DHCP reservation: вернуть только изменённые новые leases; pool/чужие MAC не менять.
- Ошибка WAN rule: выключить/удалить только два проекта dstnat, без изменений существующих маршрутов или общего firewall.
- Обновления/рост логов: отдельные диски VM, ограниченные Docker/journal/access/audit logs, Loki retention 7 дней; контролировать общий thin pool.

Создание, защищённый доступ, WAF/log приёмка, полные secure/site с `changed=0` после reboot, две ротации и последовательные reboot выполнены. Раздельные restart/outage тесты пройдены с явно записанным ограничением их сочетания. Внешний demo — по [отдельной инструкции](demo.md); публикация Git/передача доступа проверяющему остаются отдельными действиями.
