# Краткий рассказ для технической защиты

## Честный статус сейчас

Созданы две отдельные Ubuntu VM, настроены WireGuard/guest firewall/key-only SSH. Новые VPN SSH и независимые отрицательные LAN/auth-пробы прошли; commit guard clear подтверждён. Веб/WAF, Loki/Grafana/Alloy работают: HTTP 200/SQLi 403 и оба центральных log streams сопоставлены по ID. Повторные secure/site дали changed=0 на обоих узлах. Обычный restart Alloy, отдельный outage Loki и две ротации прошли. Совместный outage+restart потерял marker, а ротация кратко перезапускает WAF. Разрешённые последовательные reboot и повторная приёмка прошли; финальный post-reboot Ansible также завершился с changed=0 на обоих узлах. Retention 168h настроен, семисуточное удаление не наблюдалось. [Факты baseline](evidence/baseline.json), [полная матрица](verification.md).

По заданию SSH должен использовать ключи без root-входа и паролей, firewall должен запрещать лишние соединения, а SSH к `ubu1` должен работать только через VPN с WireGuard на `ubu2`.

Я развернул две VM Ubuntu 24.04, сейчас после обновлений 24.04.5: ubu1 с 2 vCPU/2 GiB/20 GiB и ubu2 с 2 vCPU/4 GiB/30 GiB. ## Вероятные вопросы

**Что здесь требует задание, а что выбрано нами?** Два Ubuntu-узла, ограничения SSH/firewall, WireGuard на ubu2, Ansible для веб/WAF, оба типа централизованных логов и HTTP-проверки — требования. Ubuntu24.04, VM, Loki, Alloy, hub-схема и размеры — принятые решения проекта. Домашние адреса не публикуются, версии закреплены и прочитаны runtime.

**Зачем ModSecurity и CRS?** ModSecurity исполняет правила WAF, CRS предоставляет общий набор правил распознавания атак. Наличие пакетов недостаточно: нужно подтвердить загрузку правил и блокирующий режим, а затем сопоставить ответ 403 с конкретным audit event.

**Почему Loki?** Для небольшого стенда он собирает и ищет текстовые логи без отдельного поискового кластера. Доставка и запросы проверены, production sizing и нагрузочное тестирование не проводились. Grafana нужна для просмотра, Alloy — для доставки.

**Почему недостаточно правила «разрешить SSH от VPN-подсети»?** Сетевой адрес сам по себе не подтверждает вход через VPN. Нужно проверять и входной интерфейс. Отказ из LAN проверяется отдельным новым соединением; активный SSH-сеанс может продолжать работать по established.

**Как доказать запрет root и пароля?** Проверить их через работающий VPN, где обычный пользователь по ключу успешно входит. Затем сопоставить отдельные отказы SSH, эффективную конфигурацию с учётом `Match` и серверный журнал. Отказ firewall и неверный пароль таким доказательством не являются.

**Какой IP видит WAF?** В baseline фактически10.77.42.3 — проектный WG-IP WSL. Access/audit сопоставлены по marker и transaction ID. Caller-provided XFF не считается доказательством; при изменении NAT/proxy этот тест повторяется.

**Почему HTTP 403 недостаточно?** Его может вернуть другой обработчик. Нужны соответствующее CRS-событие, реальный rule ID, блокирующее действие и корреляция с запросом. Detection-only не выполняет требование блокировки.

**Как доказана идемпотентность?** После реального развёртывания steady-state secure и site повторены: changed0/failed0/unreachable0 на обоих узлах. Bootstrap повторно не запускается на защищённом стенде, потому что он намеренно сохраняет временный путь. Для точного будущего повторения Ubuntu package state потребуется APT snapshot; здесь сохранён фактический package manifest, а приложения pinned по checksum/digest.

**Что будет с логами после рестарта или ротации?** При доступном Loki обычный restart Alloy сохранил по одной ожидаемой записи, новые marker после restart тоже доставлены. Отдельный outage Loki при работающем Alloy восстановил очередь, старый baseline сохранился. Две ротации подтвердили новые marker в активных файлах и в Loki; для pinned ModSecurity нужен короткий restart WAF, поскольку HUP audit не переоткрыл. Совместный outage Loki+restart Alloy потерял два marker при сохранённых host logs, без backfill. Lossless/exactly-once не заявляются. Семисуточное удаление ещё не наблюдалось.

**Где компромиссы лабораторного решения?** `ubu2` совмещает VPN и мониторинг и является общей точкой отказа. Для production отдельно рассмотрели бы разделение ролей, отказоустойчивость, TLS и аутентификацию сервисов, резервное копирование с проверкой восстановления, управление секретами, обновления и контроль ёмкости. Эти улучшения не подменяют обязательную часть тестового.

**Что с Telegram?** Это опциональная часть после обязательной. Условие «больше 5 за минуту» означает минимум 6 блокировок одного IP. Нужны проверка окна и защита от повторных уведомлений; один запрос нельзя посчитать дважды по access и audit logs.
