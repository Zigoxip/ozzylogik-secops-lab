# Сценарий демонстрации: 5–7 минут

Показывать фактические результаты: [исходный baseline](evidence/baseline.json) и [прямой Windows VPN через домашнюю LAN](evidence/windows-lan-vpn.json). Native Windows peer `10.77.42.4` импортирован и активен; Grafana, web и SQLi-проверка прошли. WAN DNAT остаются выключены: LAN-подключение не подтверждает внешний доступ.

1. **Схема и доступ.** Показать две VM и [схему потоков](architecture.md). Из WSL установить новые SSH-сеансы `labadmin` к `10.77.42.1` и `10.77.42.2`, проверить sudo. Показать маршруты через WG и отрицательную проверку TCP22 из обычной Windows LAN. Корневой и парольный SSH проверять через доступный VPN, чтобы не спутать отказ аутентификации с firewall.
2. **HTTP и WAF.** Из корня checkout в WSL выполнить:

   ```bash
   python3 scripts/verify-http-logs.py --web-url http://10.77.42.2
   ```

   Сохранить correlation IDs из результата. Обычный запрос должен получить 200, SQLi — 403. Сам скрипт честно проверяет только HTTP; полную приёмку завершает следующий шаг.
3. **Централизованные логи.** Открыть [OZZYLOGIK · Web & WAF](http://10.77.42.1:3000/d/ozzylogik-waf) через активный WireGuard. На дашборде видны общее число запросов, HTTP 200, подтверждённые блокировки WAF, разные IP, графики частоты, распределение HTTP-кодов и последние события. Период по умолчанию — 24 часа, обновление — 30 секунд. Loopback-автопроверки исключены; блокировки считаются по audit `transaction.is_interrupted=true`, поэтому карточка WAF не обязана совпадать с числом HTTP 403. Для проверки конкретного запроса перейти в Explore → Loki и найти маркеры предыдущего шага запросом:

   ```logql
   {job="ozzylogik", instance="ubu1"} |= "ozzylogik-"
   ```

   Выбрать небольшой свежий интервал времени. Для обычного запроса показать access event. Для SQLi показать access 403 и audit event: `secrules_engine=Enabled`, SQLi rule `942100`, blocking rule `949110`, одинаковые audit `unique_id` и access `request_id`. Проверить `client_ip`: из WSL через WG это `10.77.42.3`, из native Windows WG — `10.77.42.4`. Для Windows normal/access, SQLi/access и SQLi/audit найдены ровно по одной записи.
4. **Воспроизводимость и восстановление.** Показать фактические recaps secure/site с `changed=0`, отчёт о ротации, рестартах и согласованном последовательном reboot. Повторный reboot ради короткой демонстрации не нужен. Новая перезагрузка требует согласования.
5. **Ограничения.** Общая домашняя L2, один VPN/monitoring hub, HTTP внутри VPN, экспериментальный WAL Alloy. Обычный restart сборщика и отдельное восстановление Loki проверены; при сочетании недоступного Loki и restart Alloy в усиленном тесте потерялись синтетические события. Ротация для закреплённого ModSecurity использует короткий restart WAF. Retention 168h настроен, семисуточное удаление ещё не наблюдалось. Telegram не реализован.

## Как открыть Grafana из Windows

В установленном WireGuard for Windows уже импортирован и активирован отдельный профиль с peer `10.77.42.4/32`. Он подключается к согласованному LAN endpoint hub и добавляет только два host routes к проектным WG-IP. Default route и DNS не меняются; домашний endpoint и приватный профиль в документацию не включаются.

При активном профиле открыть вручную [Grafana](http://10.77.42.1:3000). Логин — `labadmin`; пароль находится в отдельно согласованном локальном файле пользователя. Этот файл содержит credentials и не входит в репозиторий; не показывать его при демонстрации и не копировать в чат.

Проверка выполнена native Windows HTTP-клиентом: Grafana health — 200, обычный web — 200, SQLi — 403. WAF audit подтвердил источник `10.77.42.4`, CRS rules и общий request/transaction ID. SSH tunnel и WSL localhost forwarding для этого пути не требуются. Доступ обычной LAN к TCP/22 обеих VM по-прежнему запрещён; WSL административный VPN SSH работает.

SQLi-проверку выполнять только против собственного WG web endpoint. При проблеме сначала проверить активность Windows WireGuard и два host routes; не включать WAN и не ослаблять guest firewall ради локального доступа.

## Внешняя демонстрация

Внешний доступ не проверен. До отдельно согласованного WAN demo проверить публичный endpoint и доступность UDP, подготовить внешний endpoint уже созданного peer и guest HTTP demo policy, пройти новый защищённый переход с rollback. Затем включить только две проектные DNAT-записи на время показа и проверить доступ с внешнего клиента. После показа выключить DNAT и временные demo permissions. Не менять существующие правила и не выдавать текущую LAN-приёмку за внешнюю.
