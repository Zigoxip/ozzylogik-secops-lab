# OZZYLOGIK SecOps lab

Цель — воспроизводимый стенд из двух Ubuntu VM: `ubu1` с Nginx, ModSecurity и OWASP CRS; `ubu2` с WireGuard и централизованными логами. Управление и Ansible — из WSL.

Приватный репозиторий проекта: [Zigoxip/ozzylogik-secops-lab](https://github.com/Zigoxip/ozzylogik-secops-lab). В нём хранятся Ansible, скрипты, конфигурация дашборда, документация и очищенные результаты проверок. Рабочие inventory, ключи, пароли, клиентские WireGuard-профили и исходные локальные отчёты исключены из Git.

**Текущий статус: две VM созданы, их DHCP-адреса закреплены; WireGuard, защищённый SSH и guest firewall применены, доступ проверен, rollback transaction завершена отдельным commit. WAF и централизованные логи прошли приёмку: HTTP200/SQLi403, CRS rule ID, оба log streams и общий request/transaction ID. Раздельные тесты недоступности Loki и обычного рестарта Alloy, две ротации и согласованные последовательные reboot прошли. После reboot повторно проверены HTTP/WAF, логи, SSH и порты; полные secure/site снова дали `changed=0` на обеих VM.** Исходное задание прочитано через Google Drive 23.10.2026 и сопоставлено с требованиями пользователя.

Принятые решения: две Ubuntu 24.04 VM; `ubu1` — 2 vCPU/2 GiB/20 GiB, `ubu2` — 2 vCPU/4 GiB/30 GiB. WireGuard hub расположен на `ubu2`, peers — WSL, `ubu1` и отдельный тестовый Windows-клиент, без NAT внутри туннеля. Для приложений выбраны Loki + Grafana + Alloy и официальный WAF-образ; версии закреплены в [versions.md](docs/versions.md).

## Быстрый старт

1. Прочитать [архитектуру](docs/architecture.md), [план применения](docs/application-plan.md) и [инструкцию](docs/deployment.md).
2. Подготовить WSL, закреплённые зависимости, локальные inventory и секреты вне Git. Примеры с placeholders запускать нельзя.
3. Для нового развёртывания пройти bootstrap → новый VPN-сеанс → secure → независимые проверки доступа → commit-access.
4. Только после commit запускать site и [приёмочные проверки](docs/verification.md): HTTP200, SQLi403, оба потока логов, сохранность/ротацию, повторный Ansible и отдельно согласованный reboot.

Код шести ролей и playbooks подготовлен. Тяжёлые загрузки site выполняются после снятия таймера базового доступа, чтобы не расходовать его 900 секунд. Syntax-check и успешный play recap не заменяют проверки работающих приложений.

Docker на выделенном ubu1 настроен только для host-network WAF: default bridge, Docker iptables/NAT и автоматическое включение IP forwarding отключены. Обнаруженное изменение `ip_forward` Docker-ом исправлено; после этого пройдены свежая приёмка, commit и полные secure/site с `changed=0`, `failed=0`, `unreachable=0`, включая повтор после reboot. После reboot подтверждены forwarding web=0, hub=1 и IPv6 forwarding=0 на обеих VM. Очищенные результаты — [baseline.json](docs/evidence/baseline.json).

Для наглядности добавлен [дашборд OZZYLOGIK · Web & WAF](http://10.77.42.1:3000/d/ozzylogik-waf), доступный через WireGuard. Он показывает запросы, HTTP-коды, подтверждённые audit-событиями блокировки WAF, IP клиентов и последние логи. По умолчанию выбран период 24 часа, обновление каждые 30 секунд; loopback-автопроверки исключены. Дашборд хранится в Ansible и устанавливается ролью monitoring через file provisioning, отдельно доступен tag `grafana_dashboard`.

## Ограничения

Пользователь согласовал общую LAN с guest firewall; это не отдельная L2-сегментация и не защита от root, отключившего firewall гостя. PVE firewall и существующие сервисы не менялись. Два проектных WAN DNAT созданы **выключенными**; внешняя демонстрация ещё не проверена. Домашние адреса/идентификаторы и секреты исключены из Git. Windows WireGuard использует отдельный приватный локальный профиль; по явному запросу пользователя адрес, логин и пароль Grafana также сохранены в локальный текстовый файл вне проекта. Репозиторий приватный; результаты работодателю не отправлялись. Telegram-алерт отложен.

Для Windows включён тестовый WG peer `10.77.42.4`. При активном туннеле Grafana доступна по `http://10.77.42.1:3000`, веб — по `http://10.77.42.2`. Проверены native Windows HTTP 200/SQLi403 и центральные события с источником `.4`; это тест через домашнюю LAN, без проверки WAN. Подробности — [сценарий демонстрации](docs/demo.md).

Есть подтверждённое ограничение доставки: рестарт Alloy при всё ещё недоступном Loki привёл к отсутствию тестовых событий в центральном хранилище после восстановления. Исходные host logs сохранились, backfill не выполнялся. Поэтому наличие WAL не выдаётся за гарантию отсутствия потерь при таком сочетании отказов. Обычный рестарт collector при доступном Loki, отдельная недоступность Loki и доставка после рестарта проверены успешно; в этих тестах каждая ожидаемая запись найдена один раз.

Ротация в закреплённой сборке требует перезапуска WAF: первоначальный HUP оставлял serial audit descriptor в старом архиве. Helper теперь проверяет Nginx, перезапускает контейнер и ждёт локальный healthcheck; это создаёт короткий перерыв HTTP. Две проверенные ротации сохранили доставку новых access/audit событий. Удаление данных после семи суток retention ещё не наблюдалось.
